| 200 | 7,033 | 0.999 | — | ❌ |
| 600 | 21,033 | 0.9998 | 65+ | ❌ |

## 三、根因（三项共用一条）

**`SMALL_INPUT_WHOLE_THRESHOLD = 2048`**（`src/core/compression_pipeline/methods.rs:26`）

`compress_stream`（同文件 :186-193）按输入规模三分支：

| 输入规模 | 路径 | 切片粒度 | 跨行折叠 |
|---|---|---|---|
| `> 0 且 < 2048B` | `compress_whole_input`（:225） | **整块 1 片** | ✅ 可用 |
| `>= 2048B` 且 `>= parallel_threshold` 且未开重排 | `compress_stream_parallel` | 分块→逐行 | ❌ 断裂 |
| 其余（≥2048B） | `compress_stream_serial` | **逐行切片** | ❌ 断裂 |

代码注释本身已承认这一取舍（`methods.rs:217-224`）：

> 「交互式命令输出（git status、cargo 报错、ls 等）通常**远小于** `SMALL_INPUT_WHOLE_THRESHOLD`……这里对小输入不做按行/段落切片，整块……作为单个文档切片……**保留全文上下文**」

**结论**：`rust_go_plugin::compress_cargo_test`（`methods.rs:311`）依赖「`running N tests` 头 → `test ... ok` 行 → `test result:` 尾」**同处一个切片**才能折叠。≥2048B 时该连续性被逐行切片切断 → 折叠条件永不满足 → 产物≈原文。

大输入路径虽有 `document_dispatch_seed`（:207，文档级 sticky 种子），但它**只影响插件选择，不恢复跨行结构**——故即使 rust_go 被选中，也无从折叠。

**影响面远不止 ①②③**：凡依赖跨行结构的折叠（cargo test/clippy、`ls`/`aws s3 ls` 列式、git status 多行块等）在 ≥2KB 输入下**全部失效**。三项登记实为**同一架构缺口**的三种表征。

## 四、修复方案（三选一 / 组合）

| 方案 | 做法 | 切口 | 风险 | 收益 |
|---|---|---|---|---|
| **A 文档级预折叠 Pass** | 切片前对 ≥2048B 输入先跑一次「命令族感知的跨行预折叠」，把多行结构折叠为摘要行后再逐行/分块压缩。位置类比现有 `try_two_tier_compress` 的文档级 Pass | 中（管线层新增 Pass） | 中（改动主链路，需全量门禁） | 彻底，覆盖全部跨行族 |
| **B 语义锚点切片** | 用 `StreamReader::split_by_semantic_anchors`（`stream_reader/methods.rs` 已有）把 `running N tests … test result:` 等语义块保留在同一 slice | 小（切片层） | 较低（切片策略局部化） | 精准，先解决 ① |
| **C 命令族白名单整块** | 对已知命令族放宽阈值/走整块路径 | 最小 | 低但治标 | 仅覆盖点名命令 |

**推荐路线**：**先 B（最小切口，验证收益与冻结基线影响）→ 再评估 A（彻底解）**。
C 否决：把 2KB 阈值按命令放大到 MB 级，会让超大输入退化为单切片，内存/并行收益尽失。

> 注：B 的关键是「切片边界不切断语义块」。需确认 `split_by_semantic_anchors` 是否会识别 `running N tests` / `test result:` 锚点；若不识别，则需在 rust_go 的语义签名中登记锚点。

## 八、实施期根因再诊断（2026-09-11，**推翻第三节**）

> 用户裁决 **D-1 批准、按 B 走** 后开工。实施期实测**推翻了第三节的根因假设**，故**方案 B 未采用**；真实根因落在**插件选择（detect）层**，修复为等价 3 行的锚点短路。如实记录如下（本稿为设计稿，诊断结论以此节为准）。

### 8.1 第三节错在哪里

第三节断言「≥2048B 后跨行连续性被逐行/段落切片切断，折叠条件永不满足」。三条反证：

| # | 实验 | 观测 | 结论 |
|---|---|---|---|
| 1 | 直接调用 `RustGoPlugin::compress()`（不经切片） | 整块可正常折叠 | 插件 `compress` 层无缺陷 |
| 2 | 取「`running N tests` 起至文末」的**单一整块**喂给 `detect` | 段落（整块）模式下 `detect()==None`，产物 ratio≈0.9977，**不折叠** | **即使语义块完整处于同一切片内也不折叠** → 与「切片切断」无关 |
| 3 | 打印 2047B 截断输入下的全插件 `detect` 得分 | `rust_go=0.400`、`sql=0.400`、`smart_path=0.150`、`generic_text=0.110` | 失效点是命中竞争/稀释，而非连续性 |

反证 2 是决定性的：本仓默认 `SliceMode::Paragraph`，`running N tests … test … ok` 之间无空行，**语义块本就是同一个段落切片**，不存在「被切断」。

### 8.2 真实根因：块首锚点被周围零贡献行**稀释**（两条路径同源）

`rust_go::detect` 以「前 15 行特征占比 ≥ 0.15」判归属。块首锚点 `running N tests` 仅值 2 分，而其周围行对任何特征**零贡献**：

- **段落切片路径（≥2048B）**：锚点独占段落首行，其后 N 行 verbose `test <path> ... ok` 零贡献 → `2/15 ≈ 0.133 < 0.15` → `detect()==None`，rust_go 永不被选中 → 折叠入口（`apply_advanced_compression` 的 `is_cargo_test_head` 分支）永不被执行 → 产物≈原文。
- **整块路径（<2048B）**：整段是 1 个切片，首行是 `Compiling …`，锚点在 header 之后（约第 5 行），同样被稀释到阈值之下。**更凶险的是并列歧义**：`sql` 插件对该窗口同样给出 0.4（用例名 `tests::…::insert` 撞上其 `\bINSERT\b` 头动词），而 `PluginDispatcher::detect_parallel` 的平局破平是 `priority` **升序**（数值小者优先），`sql(110)` 遂反抢 `rust_go(185)`；sql 的 `NUM_LITERAL_RE → "?"` 骨架化把 `running 140 tests` / `v0.1.0` / `2.11s` 的数字抹成 `?`（审计中「大输入 cargo test 产物全是问号」的直接来源）。

即第三节的「尺寸阈值 → 切片断裂」是**表象**：`slice_count` 由 1 跳到 65 只说明切片粒度变了，**并不蕴含语义块被切断**；真正失效点在其下游的 `detect`。

### 8.3 实际落地的修复（非方案 B）

切口在 `src/plugins/rust_go_plugin/methods.rs`：把锚点登记为**决定性短路**。判定复用既有 `is_cargo_test_head`（与折叠入口同源）：

```rust
// detect：检测窗口（前 15 行）内出现块首锚点即直接满分命中
if lines.iter().any(|l| is_cargo_test_head(l)) {
    return Some(1.0);
}
```

配套收紧 `is_cargo_test_head`（原 `line.contains(" tests")` 宽松包含 → 「`running ` + 十进制计数 + `tests`/`test`」），并让占比分支也复用它（去重复口径）：

```rust
fn is_cargo_test_head(line: &str) -> bool {
    let Some(rest) = line.strip_prefix("running ") else { return false };
    let mut parts = rest.split_whitespace();
    let (Some(count), Some(unit)) = (parts.next(), parts.next()) else { return false };
    matches!(unit, "tests" | "test") && count.parse::<usize>().is_ok()
}
```

设计要点：
1. **两路径同一条规则**：段落切片（锚点=首行）与整块（锚点在第 5 行）都命中 → 阈值两侧行为一致（边界回归由此成立）；
2. **返回 1.0 消除平局**：既跃过 0.15 阈值、又严格高于竞争对手上限（sql 0.4 / nodejs 0.85 / pytest 0.90），不再依赖 priority 升序破平；
3. **谓词收紧**：`is_cargo_test_head` 与 `compress_cargo_test` 的消费口径（`usize` 解析）严格对齐，避免 `running unit tests for parser` 一类普通文本被锚点短路满分抢占。

附带修正：`compress_cargo_test` 的 `(details below)` 后缀改为**仅在确有失败明细时**追加（原实现无条件追加，全通过场景构成「承诺了不存在的明细」的误导文本，语义门禁 rule 5/9 判定其隐藏信息）。

### 8.4 真实影响面实测（**修正第三节 §五 的冻结预测**）

对 4 个含 `running … test` 行的物理样本，实测「我的修复前 / 后」`detect` 得分与胜出插件：

| 样本 | 竞争者（修复前胜者） | rust_go 修复前 | rust_go 修复后 | 胜者变化 |
|---|---|---|---|---|
| `rust_go_plugin/case_017_cargo_test` | **pytest 0.90** | 0.40（被稀释） | **1.00** | pytest → rust_go ✅ 纠正误路由 |
| `rust_go_plugin/case_020_…verbose_large` | **nodejs 0.85** | 0.40（被稀释） | **1.00** | nodejs → rust_go ✅ 纠正误路由 |
| `shell_session_plugin/case_053_ps_cargo` | shell_session 0.40 | 0.60 | 1.00 | 不变（本就 rust_go 胜） |
| `cloud_log_plugin/case_044_non_cloud_plain` | generic_text 0.11 | 0.667 | **不命中** | rust_go 误命中被消除 ✅ |

两条关键结论：
1. **失效机制是「跨插件得分竞争」**：rust_go 被稀释到 0.40 后，被 pytest(0.90)/nodejs(0.85) 这类**无关插件**以更高分抢走——这才是「cargo test 产物≈原文」的直接原因，比「切片切断」更贴合观测；
2. **§五 的冻结基线预测未成立**：`case_017` 的**审计产物（showcase 路径）不变**、`frozen_changed=0`。原因是审计与 showcase 的产物口径是**直接对整份文件调用 `plugin.compress()`**（`showcase.rs::compress_text`），**完全绕过 `detect` 与切片层**——`compress` 自身一直能折叠。故本缺陷在审计流水线中**结构上不可见**，只能由真实管线（`compress_str`）或本稿新增的集成测试暴露。这一点同时解释了「第三节为何会误判为切片问题」：现有审计手段无法区分 detect 层与 slice 层。

### 8.5 方案 B 为何未采用

B（`StreamReader::split_by_semantic_anchors` 保语义块同片）以「块被切断」为前提；反证 2 表明语义块在段落模式下**已经**完整，加锚点切片对根因无作用。若强行实施，将引入切片策略变更却仍不折叠（正收益为零），并扩大冻结基线影响面。故不采用。

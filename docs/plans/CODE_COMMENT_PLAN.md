## 二、 核心原则（红线，永远不可违反）

### 2.1 绝对禁止事项

1. **禁止批量脚本生成注释** — 不得使用 Python/Shell 脚本批量扫描并添加注释。必须逐个函数、人工分析后手动添加。
2. **禁止整文件重写** — 添加注释时使用精确的行级替换（Edit 工具），不得读取整文件后重写。
3. **禁止修改函数逻辑** — 注释是纯文档行为，不得改动任何函数签名、返回值、内部逻辑。
4. **禁止跳过未调用函数** — 即使函数未被调用（死代码/测试代码/条件编译），只要是 `pub`/`pub(crate)`/`fn` 定义，都需要注释。

### 2.2 必须遵守事项

1. **先读指令，再动手** — 每次开始一个分计划前，必须先读取本文件和对应分计划文件。
2. **完成一个，标记一个** — 每完成一个文件/函数的注释，立即在分计划文件中更新状态。
3. **边做边验证** — 每完成一个模块的注释，立即运行 `cargo check` 确保无语法错误。
4. **发现问题，记录不修改** — 发现函数有 bug 或设计问题时，在分计划的「问题清单」中记录，不直接修改代码。

## 三、 方法论：拓扑排序 + 手术刀式编辑

### 3.1 执行顺序（拓扑排序，自底向上）

为减少重复读取和上下文切换，按依赖关系从底层到上层执行：

```
第 0 层：utils/        （工具函数，无业务依赖）
第 1 层：cli/          （CLI 层，依赖 utils）
第 2 层：core/         （核心层，依赖 utils）
第 3 层：plugins/      （插件层，依赖 core + utils）
第 4 层：bin/          （二进制入口，依赖所有层）
```

**为什么自底向上？**
- 底层模块（如 utils）被上层频繁调用，先注释完，上层分析时可直接读注释理解，无需反复读源码
- 符合拓扑排序思想：先处理无依赖的节点，再处理有依赖的节点

### 3.2 手术刀式编辑规范

对于超过 500 行的大文件：

1. **精准定位** — 先用 Grep/Glob 找到目标函数的行号范围
2. **局部读取** — 用 Read 工具的 offset+limit 只读取目标函数及其上下文（±10 行）
3. **精确替换** — 用 Edit 工具的 old_string/new_string 只替换函数签名上方的注释区域
4. **最小 diff** — 确保每次修改只产生预期的注释行变化，不触碰无关代码

### 3.3 单个文件处理流程

```
1. 读取文件（大文件分段读取）
2. 提取所有需要注释的结构（见 4.1）
3. 按依赖顺序排序（先内部函数，后公开函数）
4. 逐个函数分析调用链 → 理解功能 → 添加注释
5. cargo check 验证
6. 更新分计划状态
```

## 四、 注释范围与质量标准

### 4.1 需要注释的结构类型（按优先级）

| 优先级 | 结构类型 | 注释要求 | 示例 |
|--------|---------|---------|------|
| P0 | `pub fn` / `pub struct` / `pub enum` / `pub trait` | 必须有完整文档注释 | `pub fn run_cli() -> Result<()>` |
| P0 | `pub(crate) fn` / `pub(crate) struct` | 必须有完整文档注释 | `pub(crate) fn build_pipeline()` |
| P1 | `fn`（模块内部函数） | 必须有文档注释或行内注释 | `fn helper_function()` |
| P1 | `struct` / `enum`（私有） | 必须有文档注释 | `struct InternalConfig` |
| P2 | `#[test]` 函数 | 必须说明测试意图和验证的契约 | `#[test] fn test_edge_case()` |
| P2 | `mod tests` 内辅助函数 | 简单说明用途 | `fn setup_mock_data()` |
| P2 | `macro_rules!` | 必须说明设计意图和展开逻辑 | `macro_rules! my_macro` |
| P3 | `const` / `static` | 说明物理意义和单位约束 | `const MAX_SIZE: usize = 1024` |
| P3 | `impl Trait for Type` 块 | 说明该实现的上下文 | `impl Display for MyError` |

### 4.2 注释格式规范

**模块级注释**（文件顶部）：
```rust
//! 模块名称
//!
//! 模块功能概述（1-2 句话）
//!
//! # 主要组件
//! - StructA: 负责 XXX
//! - StructB: 负责 YYY
//!
//! # 使用示例
//! （可选，复杂模块提供）
```

**函数级注释**（`///` 文档注释）：
```rust
/// 函数功能一句话概述
///
/// 详细说明：
/// 1. 算法思路/处理流程
/// 2. 关键设计决策
/// 3. 副作用（如有）
///
/// # 参数
/// - `param1`: 参数说明
/// - `param2`: 参数说明
///
/// # 返回值
/// 返回值说明，包括 Ok/Err 的含义
///
/// # 示例
/// （可选，复杂函数提供）
```

**行内注释**（复杂逻辑内部）：
```rust
// 这里做了 XXX 操作，因为 YYY 原因
let result = complex_operation();
```

### 4.3 注释质量检查清单

完成一个函数的注释后，自问：

- [ ] 一个从未读过这段代码的人，能通过注释理解这个函数是做什么的吗？
- [ ] 参数的含义、单位、约束说清楚了吗？
- [ ] 返回值的成功/失败场景说明白了吗？
- [ ] 有副作用（修改全局状态、阻塞、IO）的函数标注了吗？
- [ ] 注释是中文吗？（项目要求）

## 五、 调用链分析方法

### 5.1 函数理解五问法

分析一个函数时，依次回答：

1. **它是谁？** — 函数签名、可见性、所在模块
2. **它调用谁？** — 内部调用了哪些函数（同模块/跨模块）
3. **谁调用它？** — 被哪些上层函数调用（可用 Grep 搜索）
4. **输入输出是什么？** — 参数含义、返回值含义
5. **核心逻辑是什么？** — 算法思路、状态转换、关键分支

### 5.2 跨模块调用追踪

当遇到不熟悉的调用时：
- 同 crate 内：用 `crate::module::function` 路径定位源文件
- 先读被调用函数的注释（如果已有），再决定是否需要读源码
- 如果被调用函数尚未注释，且对理解当前函数至关重要，**先跳过去注释被调用函数**（自底向上）

## 六、 问题清单管理

### 6.1 问题记录格式

发现代码问题时，在分计划文件的「问题清单」部分记录：

```markdown
### 问题 N：问题简要描述
- **位置**: `文件路径:行号`
- **严重程度**: Low / Medium / High / Critical
- **问题描述**: 详细说明问题
- **建议方案**: （可选）修复建议
- **状态**: 待确认 / 已确认 / 已修复
```

### 6.2 严重程度定义

| 级别 | 定义 | 示例 |
|------|------|------|
| Critical | 会导致崩溃/数据丢失/安全漏洞 | 数组越界、未处理的 unwrap |
| High | 功能错误、性能严重下降 | 逻辑错误、O(n²) 算法但 n 很大 |
| Medium | 设计问题、可维护性差 | 重复代码、命名混乱、缺乏错误处理 |
| Low | 代码风格、小优化 | 不必要的 clone、可以用 iter 代替 loop |

## 九、 常见陷阱与避坑指南

### 陷阱 1：大文件上下文丢失
- **现象**: 文件超过 2000 行，处理尾部函数时忘记了文件开头的结构
- **避坑**: 超过 1000 行的文件，先提取所有函数签名列表，打印出来作为目录，逐个勾选

### 陷阱 2：重复读取同一函数
- **现象**: 分析 A 函数时读了 B 函数，分析 C 函数时又读了 B 函数
- **避坑**: 严格执行自底向上顺序，底层函数先注释完，上层直接读注释理解

### 陷阱 3：pub(crate) 被遗漏
- **现象**: 只关注 `pub fn` 和 `fn`，忽略了 `pub(crate) fn`
- **避坑**: 每个文件处理完后，用 Grep 扫描 `pub(crate) fn` 确认都已注释

### 陷阱 4：测试模块被跳过
- **现象**: 觉得 `mod tests` 不重要，跳过注释
- **避坑**: 测试函数的业务意图很重要，必须说明「这个测试在验证哪个契约」

### 陷阱 5：宏生成代码无法追踪
- **现象**: 遇到 `derive(...)` 或 `macro_rules!`，不知道生成了什么
- **避坑**: 记录为「待确认」项，在问题清单中标注，不强行猜测
